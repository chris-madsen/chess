# Architecture Review — what remains before this is truly
# "Tal + Patricia + Maia + mating attractors"

Repository: `chris-madsen/chess`  
Reviewed HEAD: `ee815ba3dd449f67e820bcd51b5a5031f4b6cbc2`  
Date: 2026-09-19

This review is not a fresh redesign. The current architecture is already close to the intended system.

The purpose of this document is to define the remaining semantic work required before I would say:

> Yes — this is now exactly the intended architecture: **Tal + Patricia + Maia + mating attractors.**

The key principle:

> **Do not introduce another architecture swing. Preserve the roles that are now mostly correct and repair the remaining semantic inconsistencies.**

---

# 1. Intended system

```text
Exploration
    Patricia + trusted CSTal style roots

Chess/style authority
    CSTal ABSURD + CSTal EXTREME

Human response model
    Maia at target Elo

Mating direction
    Pattern Layer

Objective truth after entering a mate basin
    independent forced-mate verification
```

Pattern Layer is not a chess engine. It answers:

```text
Which admitted move moves us most strongly toward a mating attractor
after the likely human reply?
```

It does not decide whether a sacrifice is objectively sound; Tal owns that boundary for external candidates.

# 3. What current master already gets right

Current HEAD has repaired several previous architectural mistakes:

- CSTal ABSURD and EXTREME are trusted and no longer self-vetoed.
- Patricia is exploration, not chess authority.
- Patricia-only candidates still require Tal admission.
- duplicate UCI moves preserve `proposedBy[]`.
- mandatory CSTal roots cannot be starved by Patricia.
- Maia3 ranking uses deterministic settings (`Temperature=0`, `MultiPV=1`).
- Pattern scoring is family-specific MateGeometry rather than generic material/pressure rules.
- off-board requirements are filtered via applicable observed squares.
- role assignment is exhaustive/non-conflicting rather than first-piece greedy.
- global `0.97` was replaced by family-specific production thresholds.
- the 15 extended families remain catalog-only until real fixtures exist.
- discovery remains continuous: steering still chooses a move even when no target trigger is crossed.

These are the right directions. Do not undo them.

# 5. P0 — remove forced fallback from Patricia-only admission

`createUciPostMoveTacticalGate()` still has old behavior:

```text
if no candidate survives:
    choose the best exact-scored candidate
    force accepted=true
    reason=TAL_BEST_CANDIDATE_FALLBACK
```

That used to prevent the whole system from having zero candidates.

After source-aware splitting this is wrong because the gate sees only external/Patricia candidates; ABSURD and EXTREME are already trusted outside it.

Today this can happen:

```text
ABSURD  trusted
EXTREME trusted

Patricia P1 → Tal rejects
Patricia P2 → Tal rejects
Patricia P3 → Tal rejects

old fallback:
P2 → forced accepted

Pattern score for P2 wins
→ Patricia move gets selected despite Tal rejecting every Patricia idea
```

That violates the intended role boundary.

Correct invariant:

> Patricia proposes doors. Tal decides whether each external door is admissible. Zero admitted Patricia moves is valid.

Recommended implementation: add explicit gate mode, e.g.

```ts
type TacticalGateMode =
  | "ENSURE_ONE_SURVIVOR"
  | "EXTERNAL_ADMISSION";
```

Pattern steering must use `EXTERNAL_ADMISSION`, where all rejected means all rejected and no fallback is created.

Do not remove fallback globally if some legacy workflow still needs it.

Required contract:

```text
GIVEN trusted ABSURD + EXTREME
AND Patricia C,D,E
AND Tal rejects C,D,E
THEN C,D,E remain rejected
AND selected move ∈ {ABSURD, EXTREME}
AND TAL_BEST_CANDIDATE_FALLBACK is never emitted for external admission.
```

# 6. P0 — raw affinity is not a valid cross-family selection score

Production thresholds now look roughly like:

```text
ANASTASIA      .798
SMOTHERED      .902
MORPHYS        .394
HOOK           .258
DOUBLE_BISHOP  .151
```

That is already an admission that raw family score distributions differ.

Yet `familyProgress()` still chooses the family with the greatest **raw** `afterResponseScore`, and `selectPatternSteeringCandidate()` chooses the move with the greatest **raw** `afterResponseScore`.

Example:

```text
Anastasia raw=.70   trigger=.798
Double Bishop=.30  trigger=.151
```

Raw comparison says Anastasia wins because `.70 > .30`.

But relative to family calibration Double Bishop may be far deeper in its attractor than Anastasia.

So production currently has an internal contradiction:

> family scores are declared non-interchangeable for thresholds, but are still treated as interchangeable for move/family ranking.

---

# 7. Introduce a common cross-family attractor scale

Separate two concepts.

## Family-local geometry score

```text
RawGeometryAffinity(position, family)
```

This may have family-specific distribution.

It answers:

> How much does this position resemble this family's geometry under this matcher?

## Cross-family steering score

```text
CalibratedAttractorScore(position, family)
```

This **must** be comparable across families.

It answers:

> Relative to verified positives/negatives for this family, how strongly are we inside or approaching this attractor?

Only the calibrated score should compare:

```text
Anastasia vs Morphy vs Hook vs Double Bishop ...
```

Do not call it probability unless it is actually probabilistically calibrated.

Use the existing Lichess calibration data:

Fit a monotonic mapping:


```text

```

A deterministic empirical mapping is enough initially.

Later the stronger concept can become:

```text
PatternReachability(position, family, Elo)
```

# 9. Steering selection after calibration

Production selection should become conceptually:

```text
post = CalibratedAttractorScore(afterMaia, family)
before = CalibratedAttractorScore(before, family)
delta = post - before

SteeringValue =
    post
  + λ * max(delta, 0)
```

Primary: where the candidate ends up after the likely Maia response.

Secondary: whether it made positive progress.

Do not use raw delta as the main objective. `.05→.30` should not automatically beat `.75→.82` if `.82` is much deeper in a genuine mate basin.

During discovery, evaluate all steerable families on this common scale and select the best `(move, family)` pair. The family may switch every attacker ply.

# 10. P0/P1 — recognition threshold and target-branch trigger must be separated

One threshold is currently doing two jobs:

```text
A. Does this position look enough like family X to classify/report X?

B. Are we sufficiently deep in X's basin that we should freeze X
   and launch an expensive fixed-family target continuation?
```

These are different operating points.

Introduce:

```ts
patternPresenceThresholdFor(family)
patternTargetTriggerFor(family)
```

Presence threshold is for recognizer/reporting.

Target trigger is for entering a fixed-family branch.

The target trigger should be calibrated from **trajectory depth / distance-to-terminal / branch success**, not just classification at puzzle starts.

# 12. Make threshold/calibration generation reproducible

Production constants in `src/domain/patterns/thresholds.ts` should be generated by a checked-in deterministic calibration procedure.

Add something like:

```text
npm run pattern:calibrate
```

It should:

1. read calibration split only;
2. fit per-family raw→calibrated mappings;
3. derive presence thresholds;
4. derive target triggers from trajectory/basin metrics;
5. emit versioned JSON;
6. optionally generate TypeScript constants;
7. never use evaluation split for fitting.

Example artifact:

```json
{
  "modelVersion": "mate-geometry-v2-...",
  "datasetVersion": "lichess-puzzle-mvp-...",
  "family": "MORPHYS",
  "presenceThreshold": 0.41,

  "calibrationMethod": "empirical-cdf",
  "positiveCount": 8,
  "hardNegativeCount": 4
}
```

Held-out evaluation then reports how this calibration generalizes.

# 13. P1 — exact target-square role score must be maximal

Current `pieceReachability()` has slider branches that require non-zero distance for the "good line" path.

So a rook/bishop/queen already exactly on the ideal target square can fall to a low fallback score instead of `1`.

Correct base case:

```ts
if (file === 0 && rank === 0) return 1;
```

Place that before piece-specific movement logic.

Required tests:

```text
rook on ideal role square   → 1
bishop on ideal role square → 1
queen on ideal role square  → 1
knight on ideal role square → 1
```

Moving away must not increase role proximity.

---

# 14. P1 — role assignment must optimize the same objective as the scorer

Assignment search currently maximizes approximately:

```text
sum(role scores)
```

but final descriptor quality uses:

```text
minimum critical role
minimum supporting role
critical gating through min(primary, coverage)
```

Those objectives can disagree.

Example:

```text
Assignment A:
critical1=.95
critical2=.20
sum=1.15
minCritical=.20

Assignment B:
critical1=.55
critical2=.55
sum=1.10
minCritical=.55
```

Sum prefers A; pattern integrity prefers B.

Fix by scoring each feasible assignment under the same final role objective.

At minimum rank by:

```text
min critical role
then min supporting role
then sum
```

Better: compute full variant similarity for each assignment and choose the assignment that maximizes final variant similarity.

The search space is tiny, so correctness is more valuable than a shortcut.

# 15. P1 — HumanPath mate and forced mate are not the same thing

A target branch can currently become `Terminal` because Tal/Pattern versus Maia reached checkmate.

That proves:

```text
the modeled human path got mated
```

It does **not** prove:

```text
mate was forced against every legal defense
```

Both outcomes are useful, but they must be separate.

Recommended outcome:

```ts
type PatternTargetOutcome = {
  humanPathTerminal: boolean;
  humanPathMate: boolean;
  forcedMate:
    | { status: "VERIFIED"; ... }
    | { status: "REFUTED"; ... }
    | { status: "UNAVAILABLE"; ... };
};
```

Never label a HumanPath mate "forced" without independent proof.
