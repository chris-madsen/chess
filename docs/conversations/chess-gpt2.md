### Когда исходники CSTal 2 действительно понадобятся

Я бы просил их у Криса **после доказательства MVP**, примерно на Alpha/оптимизации. Они станут ценными, если мы захотим:

- давать `PatternPotential` прямо **внутрь поиска**, чтобы перспективные паттерновые ветки не были отсечены pruning раньше времени;
- менять root move ordering CSTal до начала глубокого поиска;
- использовать его внутренние search/eval features вместо повторных UCI-запусков;
- сделать pattern steering намного быстрее;
- интегрировать `PatternProgress` с его собственными жертвенными эвристиками и learned gates;
- получить 10–30 специальных кандидатов, которые CSTal сейчас может отсечь и никогда не показать наружу.

И вот последний пункт особенно важен. Внешний reranker может выбрать только среди того, **что Таль ему показал**. Если где-то существует великолепный ход:

```text
Nf5!!
CSTal root rank = 17
PatternProgress = +0.38
через 7 ходов → Anastasia forced mate
```

но CSTal наружу отдаёт только top-5, внешний слой его никогда не увидит.

Тогда уже возникает причина зайти внутрь:

```text
              сейчас, MVP
CSTal search ─────────────► top candidates
                              ↓
                         Pattern Layer


              позже
CSTal search
     │
     ├── tactical score
     ├── NNUE
     ├── sacrifice bias
     └── PatternPotential  ← наш сигнал
                 ↓
         search продолжает
```

Это гораздо более глубокая интеграция.

Поэтому я бы сейчас поменял наш roadmap в одном месте:

**MVP — исходники CSTal 2 не нужны.  
Alpha — желательно, но всё ещё не обязательно.  
Beta — тоже можно сделать с black-box CSTal.  
Исходники становятся действительно нужны только если эксперименты покажут, что внешний слой упирается в качество/ширину кандидатов или производительность.**

И это хорошая новость: **не надо ждать Криса, чтобы начинать Pattern Layer**. Мы можем построить и проверить почти всю главную идею независимо от закрытого CSTal 2.

## Есть ещё один важный момент: Tal и Maia потребляют разные ресурсы

```text
CPU
```

```text
GPU
```

Получается хороший pipeline:

```text
CPU:
CSTal worker #1
CSTal worker #2
CSTal worker #3
CSTal worker #4
...

              ↓ positions

GPU:
        Maia inference
```

То есть четыре Tal-процесса необязательно означают четыре полностью независимые Maia-модели.

Я бы наоборот в будущем сделал на каждой машине **один Maia service**, а Tal-workers посылают ему позиции:

```text
Tal #1 ─┐
Tal #2 ─┤
Tal #3 ─┼──► Maia inference server ─► replies
Tal #4 ─┤
Tal #5 ─┘
```

И тут возникает ещё одна оптимизация.

### Maia можно батчить

В один момент несколько rollout'ов доходят до:

```text
"теперь ход противника"
```

Вместо:

```text
Maia(position1)
Maia(position2)
Maia(position3)
Maia(position4)
```

по отдельности GPU можно дать:

```text
Maia([
 position1,
 position2,

 position4
])
```

одним batch.

Для Transformer это обычно намного эффективнее использования GPU.

**User:**

Бро, а возможно ли сделать какое-то кэширование, что-то типа мемоизации, например если оппонент сделал два (или более) хода в другом порядке, чем мы линию собирали, но позиция по итогу та же самая, чтобы не пересчитавать эти линии дважды заново? Или это у каких-то ботов уже есть?


---

**Assistant:**

Да, бро — **это ровно классическая задача транспозиций**, и шахматные движки давно умеют не пересчитывать одну и ту же позицию внутри собственного поиска. Но для твоего пайплайна нужен ещё **внешний, междвижковый persistent cache**, потому что CSTal, Maia и Patricia каждый по отдельности не знают, что другой уже считал ту же позицию. Я проверю, что именно есть у Patricia/Seer/Jakal, и объясню, как это лучше встроить в наш orchestrator.

---

**Assistant:**

Да, бро. Это как раз то, что нам обязательно стоит сделать. И твой пример называется **транспозицией**: разные последовательности ходов приводят к одной и той же позиции.

У обычных движков это уже есть **внутри одного поиска**. Patricia прямо документирует `Hash` как память под transposition table и MultiPV; Seer использует shared lockless transposition table с Zobrist hashing. Stockfish делает то же самое: по хэшу позиции смотрит, не считал ли уже этот узел, и при достаточной глубине может сразу использовать сохранённый результат. citeturn663896search3turn121086search0turn663896search2

Но нам нужен ещё один уровень — **транспозиционный кэш над всеми движками**.

Представь две ветки:

```text
линия A:
1. Nf3 ...Nc6
2. Bc4 ...Nf6
3. d3

линия B:
1. Bc4 ...Nf6
2. Nf3 ...Nc6
3. d3
```

Если в итоге получилось одно состояние `S`, сейчас orchestrator может сделать:

```text
S
↓
CSTal
↓
Maia
↓
CSTal
↓
...
↓
mate
```

дважды.

Нам надо:

```text
Line A → S
           ↓
        cache miss
           ↓
        считаем suffix
           ↓
        сохраняем

Line B → S
           ↓
        CACHE HIT
           ↓
        берём готовый suffix
```

То есть целая оставшаяся комбинация может вычислиться один раз.

```text

L3  Pattern cache
L4  Full rollout/suffix cache
```

Например:

```text

    │
    ├── CSTal candidates/eval считались? → взять

    │
```

Последний особенно вкусный.

Если из позиции `S` при наших фиксированных настройках уже есть:

```text

→ Rf3
→ ...Kh8

```

то повторно гонять Таля и Maia вообще незачем.

## Чем идентифицировать позицию

Не строкой PGN и не последовательностью ходов.

Обычно используют **Zobrist hash**:

```text
position → 64-bit / 128-bit key
```

Он кодирует примерно:

```text
расположение фигур
кто ходит
права рокировки
en passant
```

Поэтому две разные истории:

```text
A-B-C-D
X-Y-Z-D
```

дают одинаковый ключ `D`, если шахматное состояние одинаково.

И это очень быстро: lookup практически O(1).

---

## Но здесь есть важная тонкость

Одинаковая картинка доски **не всегда означает полностью одинаковое состояние**.

Например:

```text
piece placement identical
side to move identical
```

но:

```text
в одном случае рокировка ещё разрешена,
в другом — уже нет
```

Это две разные позиции.

То же самое с en-passant.

И ещё тоньше:

```text
halfmove clock
repetition history
```

могут влиять на ничью по правилу 50 ходов и повторению.

Поэтому я бы не делал просто:

```text
cache_key = board_fen
```

а сделал:

```text
PositionKey =
    pieces
  + side_to_move
  + castling_rights
  + en_passant
```

а отдельно:

```text
RuleContext =
    halfmove_clock
  + repetition_state
```

# Самое мощное — suffix memoization

Вот что я бы обязательно заложил в архитектуру.

Не просто:

```text
position → score
```

а:

```text
(position, policies/config)
       ↓
готовое continuation subtree / rollout
```

Например:

```text
Key:
position = 0x8A732...
Tal = EXTREME-2.07
Maia = 79M
Elo = 1900
PatternTarget = Anastasia
PatternModel = v3

Value:
Maia: ...Qe7
Tal: Rf3
Maia: ...Kh8
Tal: Rh3
...
mate in 11
```

Если любой другой root candidate через пять ходов свалился в эту позицию:

```text
HIT
```

и мы приклеили уже известный хвост.

Это почти как dynamic programming.

---

## И особенно хорошо это заработает с Patricia MultiPV

Представь Patricia дала 12 корневых кандидатов.

Через некоторое количество ходов:

```text
PV1 ───────┐
           │
PV2 ────┐  │
        ▼  ▼
          S1
          │
          ▼
          S2
          │
          ▼
         mate


PV7 ─────────────► S2
```

Когда PV7 достигает `S2`, весь остаток уже известен.

```text
PV7 → S2 → cached mate
```

В шахматах транспозиций очень много, особенно после перестановок тихих ходов.

# Более того, нам выгодно сделать глобальный shared cache

У тебя две основные машины.

Не:

```text
PC1 cache
PC2 cache
```

а:

```text
             Redis / RocksDB / PostgreSQL
                    SHARED CACHE
                    /          \
                   /            \
                 PC1            PC2
```

Например PC1 уже вычислил:

```text
hash 72AF... → Tal+Maia suffix
```

Через пять минут PC2 встретил эту позицию:

```text
cache hit
```

и вообще её не считает.

Oracle ARM с 24 GB, кстати, **вот для этого очень пригодится**.

Не надо переносить туда шахматные движки.

Он может быть:

```text
Oracle ARM
│
├── Redis
├── trajectory cache
├── pattern DB
├── task queue
└── orchestrator
```

а обе x86-машины:

```text
PC1 ──┐
      ├── Oracle cache
PC2 ──┘
```

Вот это уже хороший use-case для твоей ARM-машины.

## И ещё один очень хороший эффект

Этот cache постепенно превращается в **наш собственный graph database шахматных состояний**:

```text
Position A
 ├─ move → B
 ├─ move → C
 └─ move → D

B
 └─ Maia response → E

C
 └─ Maia response → E   ← transposition!

E
 ├─ Pattern = Anastasia .81
 └─ eventually → Mate M
```

И внезапно мы получаем почти ровно ту структуру, которую делает `deadly`, только не на абстрактных исторических матах, а на **наших Tal×Maia human-conditioned trajectories**.

Это потом станет отличным источником данных для:

\[
V(s,p,e)
\]

То есть memoization здесь даёт нам сразу **две выгоды**:

**сейчас — сильно меньше вычислений;  
потом — готовый граф для обучения Pattern/Reachability model.**

Я бы поэтому заложил Zobrist/state cache **с самого MVP**, а не добавлял его как оптимизацию потом. Это одна из тех вещей, которая одновременно ускоряет систему и формирует правильную структуру данных для Beta.
